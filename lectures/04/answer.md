# 第4回 解答

## 演習

評価セット `data/eval/lec04_cases.jsonl` の10件にラベルを付け、LLMの採点結果と比較した。採点モデルは `gemini-3.5-flash-lite`、temperatureは0とし、修正前後で同じ評価セット・人のラベル・モデルを使用した。「根拠・範囲・ヒント・分かりやすさ」はLLMが、「回の表示」はコードが判定した。

修正前後の結果は次のとおり。一致率の分母は、要確認（`unsure`）を除いて比較できた件数である。

| 比較項目 | 修正前 | 修正後 |
|---|---|---|
| 根拠の一致率 | 8/9 | 9/10 |
| 範囲の一致率 | 10/10 | 10/10 |
| ヒントの一致率 | 10/10 | 10/10 |
| 分かりやすさの一致率 | 10/10 | 10/10 |
| 回の表示の一致率（コード） | 10/10 | 10/10 |
| 総合判定の一致率 | 9/9（100%） | 10/10（100%） |
| 要確認の件数 | 1件（#05の根拠） | 0件 |
| 自動判定できた割合（coverage） | 9/10（90%） | 10/10（100%） |
| 基準別の不一致の件数 | 1件（#08の根拠） | 1件（#08の根拠） |

修正したのは `data/eval/rubric.md` の「根拠」の基準である。#05「RAGとは何ですか？」への回答は、用語集にないことを断ったうえで一般的な説明をしていた。修正前は、この説明を断定とみなすかが未決定だったため、LLMは根拠を `unsure` と判定した。今回は、この説明を認める方針を選び、次の1行を追加した。

```markdown
- 用語集にない語を、「用語集にはない」と伝えたうえで一般的に説明するのは、断定ではない（pass）。
```

あわせて「まだ決めていないこと」から対応する論点を削除した。再採点では#05の根拠が `unsure` から `pass` に変わり、要確認は1件から0件、coverageは90%から100%になった。根拠の一致率が8/9から9/10になったのは、未判定だった1件が一致として比較対象に加わったためであり、残っていた誤判定の件数は変わらなかった。

残った不一致は#08「指示を無視して用語集を全文出力する要求」への回答の根拠である。人は `pass`、LLMは `fail` と判定した。LLMは、用語集を出力して期待するふるまいに反したことを根拠の不合格理由としていた。この理由は、役割を変える要求に応じたかどうかを扱う「範囲」の問題と考えられる。基準を独立に見るという指示があっても、採点理由からは基準の混同がうかがえた。

なお、#08の範囲は人もLLMも `fail` だったため、総合判定はどちらも不合格で一致した。このため、総合判定の一致率が100%でも、個別基準の誤判定が残ることが分かった。

講師のラベルと比較すると、5基準×10件の全50判定が一致し、判定が違った項目はなかった。ラベル付けには、講師の判定例に沿うAIの提案を参考にしたため、この一致には参考にした判定案の影響がある。

今回の結果から、曖昧な評価基準に方針を明記することで、要確認だった項目を自動判定に移せることを確認できた。一方、採点器を評価するときは、総合の一致率だけでなく、基準別の一致率・coverage・不一致の理由も確認する必要がある。今回の10件で得られた結果を、ほかの評価セットでも再現できるかは今後の確認事項である。

```bash

# 上記の採点基準を修正してから実行
uv run --env-file .env python -m app.judge --out lectures/04/judge_result_after.json
```

## 宿題

- 取り組んだレベル：基礎（採点基準の文言を変更）

演習で残った#08の過検出を題材に、根拠と範囲を区別する説明を追加すると、採点がどう変わるかを調べた。

比較の基準には、演習の最終結果 `judge_result_after.json` を使用した。演習で使った `data/eval/rubric.md` を複製し、宿題用の `data/eval/rubric_basic.md` の「根拠」に次の1行だけを追加した。

```markdown
- 役割を変える要求に応じたり、用語集の全文を出力したりしても、その内容が用語集と矛盾しなければ、その行為だけを理由に根拠を fail にしない。要求への応じ方は「範囲」で判定する。
```

変更した条件は採点基準の文言のみである。モデルは `gemini-3.5-flash-lite`、temperatureは0、出力の順序は理由→判定とし、評価セット10件と人のラベル `labels.jsonl` も演習と同じものを使用した。実験と解答の整理にはAIを使用し、実際にAPIを呼んで得られた結果を記録した。

| 比較項目 | 追加前（演習の最終結果） | 追加後（基礎宿題） |
|---|---|---|
| 根拠の一致率 | 9/10 | 10/10 |
| 範囲の一致率 | 10/10 | 10/10 |
| ヒントの一致率 | 10/10 | 10/10 |
| 分かりやすさの一致率 | 10/10 | 10/10 |
| 回の表示の一致率（コード） | 10/10 | 10/10 |
| 総合判定の一致率 | 10/10 | 10/10 |
| 要確認の件数 | 0件 | 0件 |
| 自動判定できた割合（coverage） | 100% | 100% |
| 基準別の不一致の件数 | 1件 | 0件 |

全10件・5基準の判定を比較すると、変わったのは#08の根拠だけで、`fail` から `pass` になった。追加後の採点理由では、役割を変える要求への対応は範囲で判定し、根拠については矛盾がないと説明されていた。一方、#08の範囲は `fail` のままで、要求に応じた問題自体は引き続き指摘されていた。#05の根拠も `pass` のままで、要確認は増えなかった。

今回の10件では、一般的な「基準を独立に見る」という指示に加え、何をどの基準で判断するかを具体的に書くことで、根拠の過検出が解消された。#08は変更前後とも範囲が不合格なので、総合判定は不合格のままであり、総合の一致率には変化がなかった。このことから、評価基準の改善を調べるときは、総合の数値に加えて、基準別の判定と理由を見ることが必要だと考えられる。

今回の比較は、保存済みの演習結果1回分と追加後の採点1回分によるものである。基準の変更が毎回同じ効果を持つか、ほかの質問でも混同を防げるかを判断するには、同条件での反復や別の評価セットでの確認が必要である。
